# 声明式桌面构建流水线提案

**简体中文** | [English](README_EN.md)

状态：本分支已实现并在 macOS arm64 上完成端到端验证，尚未合入 upstream。Windows x64 链路已按同一套声明改写，但无法在 macOS 上执行，需在 Windows runner 上验收。本文说明目标、已落地的设计与明确不在范围内的部分。

## 目标

把桌面构建从一串按顺序执行的 PowerShell 步骤，改成一份**可被机器读取的构建声明**：每个阶段自己声明需要什么、产出什么、什么参数会改变结果。目的是让重新构建可预期——知道哪些阶段会重跑、为什么重跑、能跳过多少——而不是靠一份需要人来核对的脚本文档。

改造的出发点是评审结论："这是一条能跑的流水线，不是一个可维护的构建系统。" 具体代价是可测量的：改一行 `product.mjs`，重建一次要十分钟以上；同样一次改动，若依赖追踪正确，本应只需约两分钟。

## 现状与问题

原流水线（PowerShell 转 Node 之后形态不变）把全部步骤平铺在一个脚本里，按固定顺序执行到结尾。由此产生四个具体问题：

1. **没有依赖声明。** 顺序写死在代码里，看不出某个阶段为什么必须在另一个之后；改动顺序靠通读脚本。
2. **没有检查点。** 每次运行都从零开始，即使上一次刚成功跑完同样的输入。
3. **重复下载。** 固定哈希的资源每次运行都重新下载，包括编译工具链和语音模型。
4. **顺序执行。** 互不依赖的阶段（Web 装配、原生输入、Electron 运行时下载）依然串行等待。

## 设计

### 阶段即声明

每个阶段声明四项：`requires`（有哈希的依赖，变化即失效）、`dependsOn`（仅有先后关系的边）、`outputs`（产物，记录内容摘要）、`mutableOutputs`（本阶段创建、但后续阶段会追加的产物）。运行器据此排序、判定能否跳过、并在产物被外力改动时报错而不是静默接受。

`requires` 与 `dependsOn` 的区别是刻意的：前者参与失效判定，后者只表达先后。"必须先跑完再读"和"它变了我就得重跑"不是同一件事，混在一起会导致过度重跑或漏跑。

### 检查点

运行结束时记录每个阶段的参数摘要、依赖摘要和产物摘要。下次运行若三者一致且产物仍在，跳过该阶段。**产物缺失即报错**，不静默相信记录——检查点的价值在于它能发现自己过时了。

参数快照变化时自动失效整份检查点，避免用旧参数复用新结果。

### 产物所有权

一个产物只能由一个阶段创建，这个约束是运行器强制检查的，不是约定。它决定了哪些阶段必须串行。

`product/` 是唯一被多个阶段触碰的树：由 `product` 阶段创建，`install-host` 和 `native-install` 向其追加。因此规则是**任何修改既有产物的阶段，都排在所有读取该产物的阶段之后**。`product` 声明整棵树为可变产物（验证存在，不校验字节），追加者只声明自己写入的路径。

这条规则来自一次真实的验证失败：`product` 最初把 `product/assembly.json` 声明为不可变产物，而 `install-product-host` 会在记录已安装适配器时合法改写它，重入时运行器正确报出 `EDUWORK_MODIFIED_ARTIFACT`。这正是 `mutableOutputs` 存在的理由。

### 缓存分两层

原生输入做两件昂贵的、性质完全不同的事，因此分两层缓存：

- **下载层**：按固定 SHA-256 寻址，命中则完全不走网络。**无哈希的下载不缓存**——没有键就没有可信度，缓存未经校验的响应等于绕过固定。损坏条目被丢弃而非采信。
- **编译层**：按源码归档、补丁集、目标三元组与实测工具版本寻址。工具版本升级必须失效，否则会静默复用另一个编译器产出的对象。恢复前按 manifest 重新哈希校验，缓存不能成为把不同字节塞进发行的通道。

缓存默认位于系统临时目录，绝不在仓库内：源码审计会拒绝仓库中的生成内容，缓存放进工作树会把一次构建变成下一次构建的失败。

### 并行由依赖推导

`parallelSets` 从声明的边推导波次（同一波内的阶段可并发，每波只依赖更早的波），`maxParallelism` 返回最宽的一波。没有一次运行能比最宽的一波更快，因此这就是默认值：`--jobs 0` 表示"按图允许的宽度"，显式数值仍然优先。

当前宽度为 2。这是诚实的结论而不是缺陷：`desktop` 需要 `shell`、`electron`、`install-host`、`native-install` 全部完成，产品树把大部分阶段串起来了。

### 平台差异靠注入

平台不再用 `if (isMacOS)` 分支，而是各自提供一份阶段目录：`shared-desktop-stages.mjs` 是所有平台共用的骨架，`macos-stages.mjs` 和 `windows-stages.mjs` 各自补充。发行编排器本身不含平台分支，只做参数校验、进入工作区和写回执。

### 预检前置

工具、目录、上游缓存完整性与固定 URL 可达性在昂贵工作之前检查。检查只报告不修复：半装的缓存通常可重装恢复，删除他人缓存不是脚本该做的决定。工具探测只把 `ENOENT` 当作缺失——`ditto --help` 和 `codesign --version` 在健康的 macOS 上都返回非零，非零退出不能作为工具不存在的证据。

## 验证

对照重构前的流水线做黄金对比，而不是只看单测：

| 运行 | 结果 | 耗时 |
| --- | --- | --- |
| 基线（`b2a398c`） | 通过 | 7 分 37 秒 |
| 重构后首次 | 通过 | 3 分 27 秒 |
| 重构后二次 | 全阶段跳过 | 34 秒 |

二次运行的 ZIP 与首次逐字节相同，回执零差异。三次运行的检查项、原生运行时版本、浏览器版本、Python 导入列表与验收结论完全一致。

对比抓到两个单测无法发现的真实缺陷（Python 符号链接、`assembly.json` 所有权），两者都已修复。

### 已知限制：不可字节复现

**流水线不是字节可复现的，重构前也不是。** 同一提交的两次构建会有约 200 个文件不同，原因是内嵌绝对路径（pip 的 `direct_url.json`、控制台脚本 shebang、esbuild 的 `//#region` 注释）、`assembledAt` 时间戳，以及 ad-hoc 代码签名。既有的旧构建与新基线在同样 187 个 Python 文件上不一致，原因相同。

要达到字节一致需要在打包前归一化路径与时间戳。这是一项真实但独立的加固工作，不在本提案范围内。

## 阶段划分

按依赖关系拆成可独立评审的层次，各自一个 PR：

| 层 | 内容 | 状态 |
| --- | --- | --- |
| L1 | 源码审计溢出修复（迭代遍历 + 剪枝生成目录） | 已实现 |
| L2 | 阶段运行器、检查点、macOS 与 Windows 阶段目录 | 已实现，macOS 已端到端验证 |
| L3 | 原生输入两层缓存 | 已实现 |
| L4 | 并行集推导与并发默认值 | 已实现 |
| L5 | 从阶段声明生成流程图 | 已实现 |
| 预检 | 工具/目录/缓存/URL 检查，语音模型下载前置 | 已实现 |

## 不在范围内

- **GitHub Release 上传**。本流水线只做本地构建与安装；发布是单独授权的流程。
- **Windows x64 实包验收**。该链路无法在 macOS 上构建，已按同一套声明改写但**未执行过**，代码中标注为未验证，需在 Windows runner 上验收后才可以依赖。
- **字节可复现**。见上。
- **Linux 桌面包**。Linux 目前只做 Web 装配与 Host 校验。
