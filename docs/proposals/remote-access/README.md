# 开放远程接入协议与 Web 客户端提案

**简体中文** | [English](README_EN.md)

状态：本提案是**待评审草案，尚未实现**。文中的协议名、帧、字段、配置项、操作面划分与命令都是**设计意图**，
不代表已发布的功能或可直接使用的配置；不应按未发布的提案修改生产配置。
「已核实」标注的条目来自本机实装包的 README 与类型声明，可用文中给出的路径逐条复核；
「推断」「待验证」标注的条目尚未做源码级核对。

归属：公版（EduWork）。学校专属服务与部署细节另案，边界见[机构版边界](#机构版边界)。
关联：issue [#116](https://github.com/ECNU/EduWork/issues/116)、路线图 [#95](https://github.com/ECNU/EduWork/issues/95)。

## 评审已确认的方向

维护者在 [#116 的回复](https://github.com/ECNU/EduWork/issues/116)（2026-10-09）中确认了首阶段形态。
以下五条是**已确认的约束**，不是待讨论项；本提案正文已按它们修订：

1. **中继负责连接和转发，业务内容端到端加密。** 部署者应当可信，但**不能把 HTTPS 在中继终止
   等同于客户端到 Host 的端到端加密**。
2. **先配对，再连接。** 首次通过短时、一次性的邀请建立设备信任，**由本机确认并保存授权**；
   配对后保留设备身份，重连时证明身份并重新建立加密会话，**无需每次扫码**；
   支持**逐设备撤销**，并**使已有连接失效**。
3. **配对后可作为本人操作 Agent。** 首阶段**不必另做只读/可操作等角色体系**，
   但远程操作仍遵守该 Agent、会话和工作区原有权限，**不自动变成 full access**。
   配对管理、凭据管理等**宿主管理接口**是否开放，需要与 Agent 操作**区分清楚**。
4. **插件和 Server 都应可独立使用、公开源码。** 不绑定 EduWork 品牌、学校账号或指定公共中继；
   Server 可以**另建仓库**维护，协议和部署方式应有文档。
   ECNU 的预配置中继、学校身份与鉴权，留到公版基础完成后再扩展。
5. **防滥用与设备控制权分开。** 自托管 Server 可以要求部署者发放的接入 Key，
   但该 Key **只表示「允许使用中继」，不能代替设备配对**；
   一次性配对邀请、长期设备凭据**不应混成同一个 Token**。加密实现**优先复用现有协议和库**。

同时确认的边界：**优先零内核补丁，但不必为了「零内核改动」勉强绕过安全边界** ——
若官方接口确有缺口，把**具体缺口单独列出讨论**，不需要现在就把完整的多 Peer 能力推到上游。

## 目标

让用户从另一台设备通过浏览器查看并继续本机正在运行的 EduWork 会话、任务与工作区成果。
公共客户端与协议不绑定任何学校或服务端实现；机构或开发者可按协议自行实现接入服务。

三个必须在设计里被回答的问题（来自 #116）：

1. 复用 DSH 连接层的哪些能力，避免维护重复的内核实现；
2. 本机宿主、Web 客户端与中继/接入服务各承担什么职责；
3. 设备配对、身份认证、撤销访问、操作授权、状态同步与断线恢复如何设计。

## 一句话结论

**DSH 0.2.0-rc.2 已经把「浏览器 ↔ Host」这一整条线做完了。**
本提案不新造协议栈，而是给已有的 **Connection 载体层增加一个可远程承载的实现**，
再补上它今天明确不做的三件事：**设备身份、可单独撤销的授权、非 loopback 的传输安全。**

支撑这一结论的三条已核实事实见[与既有实现的关系](#与既有实现的关系)。

### 为什么不用 SDK 协议作底座（已核实）

`dsh-sdk-protocol` 是本仓库唯一已存在的对外协议，但它**不能**承担远程接入：

- 传输是 **stdio**，不是网络；
- 已知限制原文：「**无协议版本协商** —— 握手只携带 `serverInfo.version`（`0.0.1`，客户端不校验）」；
- 已知限制原文：「**无取消与会话关闭方法** —— 客户端放弃轮次的方式是关闭运行时进程」；
- 「**没有逐提示词结果** —— `MessageId` 只标识 inbox 准入」；
- 它没有工作区、成果、审批与设置面。

**但它的分层值得照抄**：一个纯协议库（无插件、无配置、无注册）+ 一层薄展示适配器插件，
两侧共用同一份具名类型；协议结构被 Python SDK **复现而非导入**，因此改方法/载荷时必须在同一次变更里同步对侧。

### Peer 契约刻意不记录身份与权限（已核实，本提案的立论基础）

`dsh-typert-protocol/lib/types/types.d.ts`：

```
L294  /** Opaque identity of one Peer: a party admitted to this Host by the connection
L295   *  layer. "Peer" is a connection-layer word; … */
L300  /** One Peer's session on this Host. Connection owns it: `ctx` is the Cordis …
L302   *  Peer. Who the Peer is and what it may do are not recorded here. */
L326  /** Peer the call speaks for; an in-process carrier speaks for the operator. */
L327  readonly peer: PeerScope
```

两条原文合起来说明：**「Peer」是连接层的词**；Peer 契约**只**表达「本次调用代表谁」，
**不**记录该 Peer 是什么，也**不**记录它可以做什么。

因此「远程设备 Peer」在外围实现是**契约允许**的：`OperatorPeer` 是唯一现存实现，
但契约本身没有假设只有一个 Peer，也没有假设 Peer 必须是本机操作者。
权限（what it may do）按同一段注释的划分，本来就不属于 Peer，而属于**传输层围栏 + 装配清单**。

> **注意**：`@deepseek-ai/dsh-authorization` **不是** Peer/RBAC 授权。它是「获取必须由人交出来的凭据」的
> flow 注册表（OAuth 式登录、一次性码）。它的已知限制原文写着「**没有吊销** —— 登出即
> `ctx.credentials.deleteRecord(key)`，它只遗忘本地记录而不通知签发方」。**不要把它当作设备授权的底座。**
> 值得借用的是它的范式：「seam 拥有对话，从不拥有协议」与「**交互随请求传入，而非注册表**」——
> 发起授权的一方才是能与人对话的一方，因此提问恰好抵达发问的那个界面。设备配对正需要这个形状。

### 桌面壳已经在用「壳自有的载体」（已核实其适配层）

`dsh-electron/src/native-web-host.mjs` 显示：EduWork 桌面壳**把官方 Host 起成真实的 loopback HTTP 服务**
（并断言必须是 `http://127.0.0.1:<port>`、无凭据、端口非空，否则停止 Host 并抛
`Host reported an invalid loopback address`），然后：

1. `authenticateWebHost(ready.url)` 取得 Cookie；
2. 用特权自定义协议 `dsh-app://app/...` 提供文档；
3. `forwardWebRequest(request, origin, cookie)` 把其余请求转发到 loopback origin，**注入 Cookie 与 `sec-fetch-site: same-origin`**；
4. `socketHeaders()` 只放行来自 owner `webContents` 且 `origin === 'dsh-app://app'` 的 WebSocket 升级，并改写为 origin + cookie；
5. `boot()` 返回 `{ injections, streamBaseUrl: this.#ready.origin }`。

> **证据边界**：`native-web-host.mjs` 在 `main` 上可读；但它 import 的 `./web-document.mjs` 与
> `./eduwork-native-host-process.mjs` **不在** `dsh-electron/src` 目录列表里，且
> `dsh-electron/scripts/native-desktop-source.mjs` 只改写 `main.ts` / `preload-app.ts` /
> `microphone-permissions.ts` / `fatal-recovery.ts` 四个文件、**不生成**这两个模块。
> 结合 `dsh-electron/README.md`「Electron 主进程、窗口、`dsh-app://` 和**流式 Host 传输**从该提交派生」，
> 推断 `dsh-app://` 与流式 Host 传输是 **DSH 官方桌面能力**而非 EduWork 自造。
> 此项标记为**推断**，实现前需在能跑构建的环境里核一次。

**意义**：远程载体的实现有**本仓库内可对照的先例**——同一套思路（壳/载体持有凭据并代为转发）
换成「第二台设备的浏览器」这一承载对象。

维护者评审意见：「**建议优先评估前两个，暂时不预设必须从头实现**」。
据此把原先的「一律自行实现」放宽为逐项判断：

| 处置 | 适用条件 | 当前候选 |
| --- | --- | --- |
| **直接复用源码** | 许可证明确允许、依赖可接受、不引入内核补丁、安全语义满足硬要求 | **本轮核验后无一项满足**：两个候选各有硬伤（见下两节），故暂不直接复用源码 |
| **改造后复用** | 上游交互方向正确，但安全边界不满足 | `dsh-remote-web-ui` 的配对（需改成一次性）与撤销（需主动断连） |
| **复用设计、自行实现** | 许可证不明、依赖过重、或安全语义从根本上不满足 | `ds-harness-remote` 的 **Noise IK 封装、IdentityStore 模式、最小中继转发**；`dsh-remote-web-ui` 的配对状态机、设备表落盘、零分叉复用官方 GUI |

仍然成立的约束：

- 现成实现都不完全满足本提案的四条硬要求 —— **版本化协议**、**逐设备可撤销授权**、
  **远程权限不扩大**、**断线重连不重复执行**；已核验的 `dsh-remote-web-ui` 在后两条上明确不达标。
- 直接引入会把许可证、版本线、依赖锁与长期跟进上游的责任一并带入。本仓库已有的四类复用机制
  （参考设计 / 源码内置 / fork 为独立 npm 包 / 运行时补丁，见 `docs/PACKAGES.md`）
  没有一类能在**不发布新 npm 包、不改依赖锁**的前提下直接落地 `dsh-plugins/` 内置源码扩展。
- 需要引用某个候选的具体模块时，请在评审时指定，我们按其对应的准入条件另开提案。

两条对选型有实际影响的结论：

1. **`liguobao/ds-harness-remote` 的许可证状态是分裂的。** 仓库**根目录确实没有 LICENSE 文件**
   （GitHub 因此识别不出、`/license` 返回 404），但仓库内存在 `packages/plugin/LICENSE`（**MIT**）
   与 `apps/vscode/LICENSE`，且根 `package.json` 的 `files` 字段**显式包含** `"packages/plugin/LICENSE"`。
   也就是说：**npm 发布的 tarball 里有 MIT 文本，GitHub 网页上没有**。
   严格讲，**npm 包是 MIT，而 GitHub 仓库本身的法律状态不明确**。
   若评审希望直接引用其源码，建议请作者在**仓库根目录补一个 LICENSE** 把两者对齐；
   在补齐之前按「参考设计、不复制代码」处理。
2. **`zhu1090093659/dsh-web` 的规模远超一个远程界面插件**（8,536 星标、约 1.1 GB）。
   直接引入会把一个体量远大于本功能的依赖树带进发行清单，与运行时精简方向（#119）冲突。

#### `dsh-remote-web-ui` 源码级核验结论（pin `fc2f525c`）

维护者在评审中点了三处，**逐一核实后全部成立**：

1. **没有任何业务内容加密。** 全 `src/` 无 `createCipheriv` / `crypto.subtle` / nacl / AES 调用。
   其 README 自述中继「**forwards request bytes verbatim**」，并明确承认
   「the relayed traffic passes infrastructure operated by the package author on Cloudflare's edge,
   so **the author's worker can observe it**」。
   即 **TLS 到中继为止，中继明文可见应用层内容** —— 不满足本提案的端到端加密硬要求。
   另有一处细节：WebSocket 的设备凭据走**查询串**，源站访问日志、中继与 CF 边缘都能看到该 URL。
2. **撤销是逐请求的，不会断开已建立的长连接。** 其 README 原文：
   「**Revocation is per-request**: a paired device whose request is already in flight when 停止 lands
   completes that request; the next one 403s.」门控**只在入口判定**（HTTP 入口与 WS 升级各一处），
   全仓没有「撤销即关 socket」的路径 —— 已通过的 WebSocket / EventSource 会存活到对端自行关闭。
3. **撤销边界不覆盖直连官方 `/api`。** 其代码注明「NOTHING emits api/gate in the official runtime」，
   并打印警告「stop() does not revoke an already-redeemed browser credential」。
   也就是说撤销只作用于插件自己的 `/remote` 通道与配对 cookie，
   **设备此前兑换到的 harness 浏览器凭据不受影响**（自然过期 30 天）。
   把它当作「全局踢下线」会留下一个无人管辖的入口。

**可借鉴的部分**（质量不错，值得按其思路实现）：

- 配对状态机是纯 TS + 注入时钟与随机源，**安全语义可单测**；
- 落地页 grant 用 **delete-before-validate** 实现真正的一次性 —— 一次性配对邀请可照此写法；
- 设备表以 `{ mode: 0o600 }` + 原子改名落盘，撤销落盘失败即删档；
- **不打包官方前端产物**，改为运行时抓本机回环的官方 index 并注入脚本，原文：
  「The QR link is the official Web GUI itself ... so **the remote surface can never drift from the
  official one**.」—— 这是**零分叉**的做法，比本提案原先设想的「复用 `dsh-web-frontend/dist`」
  更稳：官方前端升级时不会分叉。**采纳为客户端边界的首选方案**（见[客户端边界](#客户端边界)）。

#### `ds-harness-remote` 源码级核验结论（pin `b2beef0c`）

**它是四个候选中唯一真正实现了端到端加密的**，这一层值得采纳：

- **标准 Noise IK**：`Noise_IK_25519_ChaChaPoly_SHA256`，外包一个**维护中的第三方实现**
  （`@lukeburns/clatterjs`），**自己不写握手状态机**；suite 名不符即抛错。
- **静态公钥 pinning**：构造时锁定远端静态公钥，每次读写后做**常数时间比对**，失配即销毁会话。
- **prologue 绑定上下文**：`DSH-REMOTE\0v=1\0connection=…\0host=…\0client=…`，防跨连接/跨设备移植。
- **中继确实看不到内容**：中继只校验 `counter` 递增后**原样转发密文**，
  转发载荷字段仅 `connectionId / targetDeviceId / counter / ciphertext`。
  中继可见的是账号、deviceId、角色、显示名、**公开身份公钥**、在线状态、连接时间、
  frame 大小与方向时序；**看不到**提示词、会话、工具输入输出、workspace 路径与私钥。

**但它的信任根在 Server 侧 —— 这正是 #116 要改掉的地方：**

- 私钥确实本机生成且从不上传，但**对端身份由 Server 返回**：`handleConnectIncoming`
  先向 Server 回查对端 descriptor，再据此写入本机 pinned trust。
- **首次连接直接写 pin，没有任何本机人工确认。** 其文档把这点写死了：
  「不存在额外设备码、确认事件或本机人工确认 UI」。
  于是「本机信任」实际是**自动信任 Server 的断言** —— Server 在首次连接返回伪造 descriptor 即可 MITM。
- **改成本机配对授权的工作量：中等偏小（约 150–300 行 + 一个确认界面），但有一个真正的难点** ——
  其 `connectionId` **由 Server 生成**并进入 Noise prologue。若要让授权完全脱离 Server，
  这一层必须一并改造（改由本机生成并经带外传递）；否则只是把「自动信任」换成「界面上点一下确认」，
  **安全性质没有变化**。
- 结论：**它的加密层值得借鉴，授权层不可照搬。**

**其他需要留意的事实：**

- **不打内核补丁**，但其集成**依赖若干非完全公开的接口形状**：`ctx.loader.entries()`、
  settings 的双代 `register` / `configure` 分流、`webServer` 与 `typertGateway` 靠类型断言取得。
  这些是跟随 DSH 升级时的主要破点；本提案应采用更保守的注入方式。
- `serverUrl` 的默认值 `https://dsh.r2049.cn` 是**可配置默认，不是硬编码**；
  但**改 URL 会切换设备身份目录**（按 server origin 哈希隔离），等于需要重新配对。
- 其中继参考实现很小（约 422 行、环境变量配置、不存密文），但自托管形态是
  **relay-only**（`webrtcEnabled: false`、无 TURN 端点），WebRTC 直连路径在自部署下用不上。
- `werift`（锁死精确版本）是 Host 侧 WebRTC 实现、懒加载；在 relay-only 自部署场景属于**死重量**，
  也是其 1.56 MB bundle 的主要来源。**本提案不引入它。**

#### `dsh-plugin-remote` 与 `DSH-Remote` 源码级核验结论（pin `19ffcc29` / `edf350e1`）

**两个项目都只有「单一共享凭据」，都没有设备概念 —— 这恰恰印证了 #116 要补的空白。**

| | `siberiah2o/dsh-plugin-remote` | `ChongYep/DSH-Remote` |
| --- | --- | --- |
| 分层 | 三层：插件宿主半 → **独立网关子进程**（自监听 `0.0.0.0:4080`）→ 浏览器半；HTTP + WebSocket 反代 | 无代理层，**直接改 DSH 自身**；公网由 `tailscale serve` 终结 TLS 后回源 loopback |
| 认证 | **自建账号**（scrypt + HMAC Cookie），多账号，会话 7 天，撤销靠 `sessionEpoch` 递增 | **单一部署级 Bearer token**，脚本重启即换新 token |
| 设备概念 / 配对 | **无** | **无** |
| 内核补丁 | **无**（`dsh.bundle.patch` + `dsh.client`） | **有，11 个 DSH 源文件**，基线锁死 `5badb15009` |
| 业务级幂等 / 重放保护 | **无**（仅传输层保活 + 进程自愈） | **无**（仅壳层可达性探测 + 重试按钮） |
| 端到端加密 | **无**。TLS 可选且需自备 PEM，默认明文；网关是 TLS 终点，**能解密并改写正文** | 公网模式 WireGuard + 真证书 TLS **双层**；LAN 模式明文 HTTP |
| 许可证 | 根目录**无 LICENSE**（README 与 `package.json` 声称 MIT） | 根目录 **MIT** ✓ |

**值得借鉴的零件**

- `dsh-plugin-remote`：`gateway/websocket.mjs` 的 **RFC6455 服务端**（自带，不引依赖）、
  `gateway/server.mjs` 的 **scrypt + HMAC + `sessionEpoch` 撤销 + 限流**、
  `lib/index.js` 的**子进程托管**（健康轮询 / 退避 / 孤儿回收）。
- `DSH-Remote`：新增的 `packages/client/connection/src/web-token.ts` —— **同一令牌的三分支承载**
  （`Authorization` 头 / WebSocket 子协议 / `?token=` 换 Cookie）+ `timingSafeEqual`，
  是「在 DSH 准入点做校验」的现成参考。
- 部署层最省事的路线：**`tailscale serve` + loopback**（不开公网端口、真证书自动续期）。

**为什么它们替代不了本提案**

- `dsh-plugin-remote` 自己承认 `/api` **没有中间件缝隙**可占（`lib/index.js`），所以只能在前面挡一层；
  而它的网关**能解密改写正文**，说明那只是应用层代理，**远端浏览器仍拿不到 DSH 凭据**。
- 两者**都没有设备身份**，因此「先配对再连接」与「逐设备撤销」**必须自研**。
- `DSH-Remote` 的 11 处补丁**全是 DSH 内部路径且锁死单一基线**，升级即冲突；
  它还**改写了上游拒绝 `--host 0.0.0.0` 的安全默认** —— 这正是「优先零内核补丁」的理由。

**⚠️ 一个直接影响本提案客户端方案的坑**

`dsh-plugin-remote` 的做法是**往反代的 HTML 响应里就地注入脚本**。但 DSH web profile
**默认开启 gzip** —— 本机实装包 `@deepseek-ai/dsh-web-app/cordis.patch.yml` 第 175–177 行：

```yaml
compression: gzip
compressionLevel: 1
compressionThresholdBytes: 1024
```

**就地改写会破坏压缩正文。** 因此本提案的客户端路线是
「**从本机回环取官方 index，解压后在服务端完成注入，再自行下发**」，
而**不是**在反代链路上改响应。这条已写入[客户端边界](#客户端边界)。

> （`fc2f525c` / `b2beef0c` / `19ffcc29` / `edf350e1`），结论均带文件与行号证据。

## 协议草案 `eduwork-remote/v1`

### 握手

握手分**两层**：先在设备与 Host 之间建立 Noise IK 加密信道，**再在该信道内部**做本应用的协议协商。
应用层的 `hello` / `welcome` **只在加密信道内传递**，中继永远看不到。

#### 第一层：加密信道

- **套件 `Noise_IK_25519_ChaChaPoly_SHA256`**，**外包一个维护中的成熟实现，不自行编写握手状态机**
  （`ds-harness-remote` 的做法，已核验：它包了一个第三方 Noise 库并校验套件名）。
- **静态公钥 pinning**：两端各自锁定对端静态公钥，每次读写后做**常数时间比对**，失配即销毁会话。
- **`prologue` 绑定上下文**，至少含协议版本、`connectionId` 与双方 `deviceId`，防跨连接/跨设备移植。
- **会话密钥每次连接重新协商**，不复用上一连接的状态。

> **与 `ds-harness-remote` 的关键差别**：它的 `connectionId` **由 Server 生成**并进 prologue。
> 本提案要求 `connectionId` **由 Host 生成并经带外（配对邀请）传递** ——
> 否则授权仍依赖 Server 的断言，「本机决定授权」就是空的。
> 这是本提案与它的**根本分野**，详见[设备配对与身份](#设备配对与身份)。

#### 第二层：应用层协商

```
客户端 → Host
{ "type": "hello",
  "protocol": "eduwork-remote/v1",
  "deviceId": "<已配对设备的稳定标识>",
  "client": { "name": "示例设备", "platform": "browser|android|ios|desktop",
              "appVersion": "0.1.0" },
  "capabilities": ["stream.v1", "events.v1", "journal.v1"] }

Host → 客户端（成功）
{ "type": "welcome",
  "protocol": "eduwork-remote/v1",
  "host": { "home": "<用于缩写路径>", "appVersion": "0.4.2",
            "dshVersion": "0.2.0-rc.2" },
  "session": { "id": "<本次远程会话标识>", "expiresAt": "<绝对时间>" },
  "surfaces": { "agent": ["session:list", "session:read", "session:prompt"],
                "host": [] },
  "resume": { "supported": true, "cursorTtlMs": 600000 } }

Host → 客户端（失败）
{ "type": "reject",
  "code": "unauthorized" | "revoked" | "version-unsupported" | "surface-empty",
  "message": "…" }
```

`surfaces.host` 默认为**空数组**（宿主管理面默认不开放），见[操作面划分 v1](#操作面划分-v1默认拒绝)。

### 版本与能力规则

- 双方各自声明 `protocol`。**主版本不同即拒绝**（`version-unsupported`），**不做自动降级**。
  这与仓库既有取向一致——网关认证提案原文：「未知版本、冲突标志或缺少关键能力必须报错，不在授权失败后自动降级。」
- `capabilities` 取交集；客户端**不得**在 Host 未声明某能力时发送对应帧。
- **数据面帧格式复用 `dsh-api-gateway/stream-protocol`**，不另立一套：

  ```
  Client→Host: open{streamId,endpoint,payload} | item{streamId,value?} | end{streamId} | cancel{streamId}
  Host→Client: item{streamId,value?} | error{streamId,error{code,message,details}} | end{streamId}
  ```

  v1 只在其**外面**加一层握手与操作面声明。**不要在该帧里新增版本字段**——版本属于握手，
  帧保持与浏览器客户端逐字一致，才能共用解析器。

### 幂等与恢复（对应验收项「断线重连不会重复执行操作」）

- **有副作用的一元调用**（v1 中即 `session:prompt` 一类）必须携带客户端生成的 `requestId`。
  Host 在 TTL 内按 `(deviceId, requestId)` 去重：重复到达返回**同一结果**，不产生第二条用户消息。
- **流**复用 `ctx.remote.$stream()` 家族：`RemoteJournalStream` 提供 follow-before-page、分页、
  重连追赶与缺口修复，并**丢弃完整重复项**、拒绝缺口与倒置区间。
- 上游既定事实（已核实）：「**单向通知不会重放**……需要可靠恢复的状态必须由拥有方提供查询、游标或初始基线。」
  因此**状态同步必须由 Host 侧提供查询面或游标**，不依赖通知补发。这是设计要求，不是可选优化。
- 另两条上游限制决定了不能靠重放：（a）「上行项**不会跨载体代际重放**，需要恢复上行的领域在重开的请求里自带确认游标」；
  （b）`websocketHeartbeatIntervalMs` 同时是 Ping 周期与 Pong 截止时间，网络可能停顿超过该间隔的部署**必须调大**该配置。

### 操作面划分 v1（默认拒绝）

**首阶段不引入只读 / 可操作等角色体系**（维护者已确认）。配对成功后，该设备**即可以本人身份操作 Agent**；
但「可以作为本人操作」**不等于**「能操作一切」：远程操作**沿用该 Agent、会话与工作区原有的权限**，
**不自动变成 full access**。把操作面按下面两类分开，是这一条在实现里可被验证的方式。

| 类别 | 内容 | v1 默认 |
| --- | --- | --- |
| **Agent 操作面** | 列出/读取会话、投递用户消息（有副作用，需幂等键）、取消轮次、列出/读取已登记工作区文件、读取与下载 Studio 成果、读取设置（不含凭据） | 配对后可用，**但仍受该 Agent / 会话 / 工作区既有权限约束** |
| **宿主管理面** | 配对与设备管理、凭据读写、插件安装/卸载、终端、`workspace:write`、设置写入 | **默认不开放**；是否在首阶段开放需单独确认 |

**为什么必须把宿主管理面单独列出**（维护者已确认）：配对管理、凭据管理这类**宿主管理接口**
与「操作 Agent」是两件事 —— 前者管的是**谁能连进来**，后者管的是**连进来之后能做什么**。
两者混进同一个授权，等于让「能聊天」隐含「能改谁能连进来」。

`approval:respond`（响应审批提示）同样单列：让远端设备代替本机点击「允许」等价于间接提权，
因此**独立列出、默认不授予**。

理由：#116 原文要求「**远程操作应延续本机权限，不能自动扩大授权**」。默认拒绝 + 显式授予，
是唯一能在实现里被验证的满足方式。

### 设备配对与身份

**先配对，再连接**（维护者已确认）。四类凭据**必须彼此独立，不得混成同一个 Token**：

| 凭据 | 作用 | 生命周期 | 能否代替配对 |
| --- | --- | --- | --- |
| **中继接入 Key** | 表示「允许使用这个中继」，由中继部署者发放 | 由部署者管理 | ❌ **不能**。它只解决防滥用，不代表设备已被信任 |
| **一次性配对邀请** | 首次建立设备信任的入场券 | **短时、用过即失效** | 它本身就是配对入口 |
| **长期设备凭据** | 配对后证明「还是这台设备」 | 长期，可**逐设备撤销** | 是配对的结果 |
| **会话密钥** | 单次连接的业务加密密钥 | 单次连接 | 每次重连都要重新协商 |

流程：

1. 本机 EduWork 打开「远程连接」面板，生成**一次性、短时效**配对邀请；
2. 在另一台设备打开接入地址，输入/扫描该邀请；
3. 该设备在**本地**生成非对称密钥对（WebCrypto，私钥不可导出），把**公钥** + 设备名发给 Host；
4. **Host 侧必须由人在本机确认**，界面显示设备名与将被授予的操作面 ——
   **设备授权由运行 Agent 的本机决定**，不由中继转述；
5. 配对完成后颁发**长期设备凭据**；此后重连**不再需要扫码**：用 **challenge-response 签名**证明
   身份，并**重新协商会话密钥**，**不使用长期 bearer token**。

**「邀请一次性」是有意为之**：邀请若在有效期内可重复使用，等于**任何拿到它的人都能变成一台新设备**。
用过即失效把「邀请泄露」的后果收窄成「一次，且必须抢在真设备之前」。

### 撤销

撤销一台设备 = **让它此刻仍然活着的连接也立刻失效**，而不是只拒绝它接下来的请求。两条动作必须同时生效：

1. **拒绝新请求**：该设备的长期凭据即刻作废，后续 challenge-response 一律不通过；
2. **切断已建立连接**：Host 主动关闭该设备当前的全部活动连接，作废相应会话密钥，并让中继侧同步断开。

> 维护者在评审中点名了这一条：撤销边界「**不能只验证新请求被拒绝**」。
> 只做第 1 条的实现，在验收项「撤销授权后连接失效」下**不通过** ——
> 一条已建立的长连接可以继续收事件、继续投递消息。

**为什么设备凭据必须是独立于 Cookie 的第二套**（已核实）：现有连接层「**没有 logout 操作**」——
清除浏览器 Cookie 只结束一个浏览器会话，撤销全部会话需要「删除 owner 凭据记录并重启 `dsh`」。
用 Cookie 做远程认证将**无法**满足验收项「撤销授权后连接失效」。
同时，Cookie **刻意不加 `Secure`**（因为随附服务器走 loopback HTTP），上游原文已警告
「把同一 authority 暴露到明网传输上会让 bearer cookie 在途中泄露」。

### 传输安全边界

**中继只负责连接和转发，业务内容端到端加密**（维护者已确认为硬要求）。

- **端到端加密是独立于 TLS 的一层。** TLS 在中继终止时，中继拿到的是明文业务流量 ——
  **「HTTPS 到中继为止」不等于端到端加密**，两者不能互相替代。
- **加密端点只能是设备与 Host。** 中继即使被攻陷、或由他人运营，也**只能看到连接元数据**
  （谁在何时连了谁、流量大小与时长），看不到提示词、回复、文件内容与成果字节。
  这是**架构保证**，不是「承诺不看」。
- **候选握手：Noise IK**（`ds-harness-remote` 已采用的做法，见[社区方案对比](#社区方案对比)），
  或其它提供相同性质、经过审查的成熟实现。**优先复用现有协议与库，不自行发明密码学。**
- 必须一并给出的还有：**静态密钥的生成、保管与固定（pinning）**、**密钥轮换**、
  **多设备下每设备独立密钥**，以及**设备撤销后相应密钥材料的作废**。
- 本机侧继续**只**绑定 `127.0.0.1`；`dsh web --host 0.0.0.0` **保持不支持**，本提案**不放松** loopback 围栏。
- 远程载体是本机进程内的**第三个载体**，对外只经中继或用户自建的隧道；
- 公版不内置公网 TLS 证书管理；
- `trustedHosts` **不用于**远程接入（已核实：它必须是 canonical bare authority，**没有通配语义**，
  且非规范写法会让插件加载失败）。

## 会话与文件访问边界

- 远程客户端**只能**访问 `session:list` 返回的会话与 `workspace:list` 返回的文件；
  不提供任意路径读取，避免变成通用的本机文件读取面。
- 工作区文件读取沿用现有 `dsh-fs` 与 `dsh-fs-sandbox` 的边界，**不新开旁路**。
- 成果下载沿用 Gateway 的附件与精确 Fetch 路由机制（含 range 与流式响应），不另建下载通道。
- 审计记录留在本机，本机界面可见；**不写入会话日志**，避免把设备信息带入模型上下文。

## 客户端边界

- **首选：零分叉复用官方 Web GUI。** 已核验的 `dsh-remote-web-ui` 给出了一条比打包产物更稳的做法 ——
  **运行时向本机回环抓取官方 index 文档，并注入一段引导脚本**；远程界面因此**永远是官方那一个**，
  官方前端升级时不会分叉。其原文：「The QR link is the official Web GUI itself ...
  so **the remote surface can never drift from the official one**.」
  这优于本提案原先设想的「打包复用 `dsh-web-frontend/dist`」：打包会随官方升级产生版本漂移。
- **落地时必须绕开 gzip**（已在本机实装包核实）：官方 web profile **默认开启 gzip** ——
  `@deepseek-ai/dsh-web-app/cordis.patch.yml` 第 175–177 行是
  `compression: gzip` / `compressionLevel: 1` / `compressionThresholdBytes: 1024`。
  已核验的 `dsh-plugin-remote` 正是在**反代链路上就地注入**，那条路会被压缩正文破坏。
  因此本提案的做法是：**先把官方 index 完整取回并解压，在服务端完成注入后再自行下发**，
  **不在反代链路上改写响应**。
- **可复用性的依据**（已核实）：`ctx.remote` 明确被设计为「**不依赖 React** 的约定」，
  上游原文亦称「Web 或**未来的 TUI** 只要提供同一份约定，均可复用其 Client face」。
- **退路**：若运行时抓取不可行（例如官方 index 的注入点在目标版本不存在），
  退回构建一个只依赖 `ctx.remote` 约定与 `stream-protocol` 解析器的精简客户端。
  **最终取舍留待评审确定**，见[尚待明确](#尚待明确)。
- 移动浏览器适配：目标基线为移动端主流浏览器；桌面壳与 `file://` / `dsh-app://` 相关行为**不适用**于远程客户端，
  需独立验收。已核验的适配触发条件可作参考：竖屏 + `pointer: coarse` + 视口宽 < 1100px。
- **已知脆弱点（采用该路线即需承接）**：
  - 其适配层用官方 CSS Modules 的**语义后缀选择器**定位元素，官方重命名语义类名即失效，
    **每次官方 GUI 升级都需要视觉回归**；
  - 注入依赖「官方 index 能被完整取回并解压」这一前提 —— 若官方将来改用流式压缩、
    或把引导点移出 HTML 文档，注入即失效。此时退回独立精简客户端（见上）。

## 部署方式

四级形态，**复杂度递增、能力不递减**：

| 级别 | 做法 | 需要新增的服务 | 新增端口 | 典型链路 |
| --- | --- | --- | --- | --- |
| **L0 同 LAN** | 同一局域网直连 | 无 | 一个内网端口 | 局域网 |
| **L1 已有 VPN** ⭐ | 本机与远程设备都加入**用户已有的** VPN | **无** | **无**（复用既有隧道） | 由用户 VPN 决定 |
| **L2 自建反向代理** | 在用户既有的反代上**只增**一条指向本机 `127.0.0.1` 的路由 | 一个绑回环地址的轻量进程 | 无（复用既有 443） | 公网，受跨境/上行带宽限制 |
| **L3 信令与数据分离** | L2 只承载信令；数据面直连打洞或回到 L1 | 同 L2 | 无 | 直连 |

**L1 是推荐首选**：它不需要部署任何新服务、不需要新开端口、不引入新的合规面，
只要求用户已有的 VPN 两端可达。本提案不要求用户为此采购任何东西。

### 中继应当拆成两条路径

这是从真实链路约束反推出来的设计，不是偏好：

| 路径 | 承载 | 对链路的要求 | 可由谁承载 |
| --- | --- | --- | --- |
| **信令 / 会合** | 配对码交换、设备公钥登记、端点发现、在线状态 | 极低（字节级，容忍高延迟） | 任意小配置反代，够用 |
| **数据面** | 会话事件流、提示词、成果字节 | 高（带宽 + 低延迟） | 直连打洞、用户 VPN，或局域网 |

**附带的安全收益**：数据面不经过中继时，中继**在物理上**就看不到内容 —— 这比「承诺不看」可靠。

### 中继实现的硬性约束

- **必须极轻量**：中继可能跑在内存只有几百 MB 的共享小机器上，不得要求重型运行时、
  不得要求在中继主机上构建，不得引入容器编排依赖。
- **必须与既存服务共存**：中继很可能与用户其他服务共用一台反代主机。
  因此接入方式必须是**只增不改**（追加自己的路由/上游），并且**不得要求整份重载反代配置** ——
  整份重载会冲掉只存在于运行时、未写入配置文件的路由。这一点在真实共享主机上是已被验证的坑。
- **部署位置与合规由部署方决定**：部分司法辖区要求面向公众的 Web 服务完成备案，
  而私有 VPN 端点不受此限。因此协议**不假定中继的地理位置**，
  只要求「中继可由机构或开发者自行选择部署位置，并自行承担当地合规要求」。
- **中继不可信**：设备身份在**端到端**层面校验（challenge-response 签名），
  不依赖中继转述的身份。业务内容端到端加密，中继**只能看到连接元数据**。
  中继被攻陷不得导致越权，也不得导致内容泄露。
- **不绑定品牌、账号与公共中继**（维护者已确认）：中继可由任何人自建，
  不绑定 EduWork 品牌、学校账号，也不指定唯一的公共中继；协议与部署方式须有文档。
  **中继 Server 可以另建仓库维护**，不进本仓库的发行清单。
- **接入 Key 只用于防滥用**（维护者已确认）：自托管中继可以要求部署者发放的接入 Key，
  以避免未经允许的接入；但该 Key **只表示「允许使用这个中继」，不能代替设备配对**。
  它与一次性配对邀请、长期设备凭据是**三种不同的东西**（见[设备配对与身份](#设备配对与身份)）。

### 「通用客户端不绑定学校服务」的落地方式

客户端只认 `eduwork-remote/v1` 与一个接入地址，**不内置**任何机构域名、登录方式或服务发现；
机构差异全部落在中继与机构版插件里。

这一条同时是 `CONTRIBUTING.md` 对公版的硬要求，逐项对应如下：

| 要求 | 本提案如何满足 |
| --- | --- |
| **不依赖机构凭据** | 通用插件不读取、不要求任何机构身份或令牌；设备凭据由用户在本机自行创建与保管 |
| **不依赖私有网络** | 中继是**可选组件**；同一 LAN、用户自有的 VPN、端口转发都必须能在**没有中继**的情况下工作 |
| **不依赖相邻源码仓库** | 全部实现位于本仓库 `dsh-plugins/`，不引用 EduWork-ECNU 或任何外部仓库 |

用户自有基础设施（VPN、反向代理、服务器）属于**用户侧的部署选择**，不是公版产品的依赖：
公版代码路径**不得探测、假定或要求**任何特定外部服务存在。

## 兼容性边界

- 新增一个独立宿主插件与一条新增的远程载体，**不修改**现有插件的公开导出、配置标识与数据路径。
- **不修改** `BrowserAuth`、`api-request-trust` 的 loopback 围栏语义，**不修改** `dsh web` 的 host 行为。
- **不新增**运行时依赖，**不改**依赖锁。**是否新增一个需单独发布的 npm 包，取决于插件布局的结论**
  （见[尚待明确](#尚待明确)）：放 `packages/` 则新增一个独立 npm 包，并承担其版本、peer 范围与
  provenance 发布流程；放 `dsh-plugins/` 则作为内置源码扩展在装配时重建，不新增 npm 包。
- 若放 `dsh-plugins/`：发行清单新增一行插件登记，不改变既有插件的顺序与配置；
  两种布局都无历史数据迁移（首次引入）。
- 唯一需要评审的公开接口是 `eduwork-remote/v1` 的握手与操作面划分。
- 桌面端与机构版行为不在本提案的实现范围；桌面行为需独立验收。

## 不做什么

- 不新增 RPC 协议或帧格式；不复制 Gateway 的 mux 与退避策略；
- 不修改 `BrowserAuth` 与信任围栏；不把 `--host 0.0.0.0` 变成受支持的部署姿态；
- 不在公版实现学校 SSO 或机构服务发现；
- 不引入第二套桌面壳。

## 开发拆分与验收

阶段划分：**先文档、后骨架、再协议、最后中继**。每个 PR 报告**实际执行的验证与未验证范围**。

1. **本提案（仅文档）**：`docs/proposals/remote-access/README.md` + `README_EN.md`。
   运行 `node scripts/check-source-docs.mjs`。本 PR 不含任何代码。
2. **骨架插件**：`dsh-plugins/remote-access/`，注册「远程连接」设置面板与设备登记表的本地 CRUD，
   配对只在同 LAN 内用合成数据跑通；不改协议。验收：面板可用、登记表重启后保留、`node --test` 单元测试。
3. **配对与授权**：一次性邀请（**delete-before-validate**）、本机确认界面、长期设备凭据、
   challenge-response、**撤销时主动断开已建立连接**。
   验收：单测覆盖邀请不可重放；撤销后**活动连接被关闭**，而不只是新请求被拒。
4. **端到端加密**：握手选型、静态密钥生成/保管/固定、会话密钥协商与轮换、撤销后密钥材料作废。
   验收：合成契约测试 + **中继侧断言看不到业务明文**。
5. **协议与恢复**：版本协商、能力交集、操作面围栏、幂等键与 `RemoteJournalStream` 恢复。
   验收：合成契约测试（版本不匹配报错、能力缺失拒绝、未授权 endpoint 被拒）。
6. **中继参考实现**：最小自托管 server，**不进公版发行清单**，可放独立仓；
   **接入 Key 与设备配对严格分离**。
7. **Web 客户端**：配对 UX、设备凭据、移动浏览器适配。

**#116 验收关注 → 验证方式**（每条都要能被别人重复）：

| 验收项 | 怎么验 |
| --- | --- |
| 跨设备继续同一任务 | 设备 A 发起轮次 → 设备 B 列出并读取该会话 → 从 B 投递一条消息 → 断言轮次在同一会话上继续、且设备 A 界面实时反映 |
| 断线重连不重复执行 | 在投递进行中断网 → 重连后重发同 `requestId` → 断言会话中**只有一条**用户消息 |
| 未授权设备不能访问 | 无凭据 / 错误凭据 / 未配对各跑一次 → 断言在任何 RPC 分发**之前**即被拒（401/403），且**没有任何会话或文件字节**过线 |
| 撤销授权后连接失效 | 撤销设备 → 断言**已建立的长连接立即被关闭**（WebSocket 与流式订阅不再收到事件）、该设备会话作废、重新认证失败。**只断言「新请求被拒」不算通过** |
| 邀请不可重放 | 用同一配对邀请二次配对 → 断言第二次失败，且失败发生在**校验**而非仅界面提示 |
| 中继看不到内容 | 在中继侧抓取被转发的字节 → 断言只有密文与连接元数据，**不含提示词、回复与文件内容** |
| 远程不扩大授权 | 远端尝试宿主管理面（凭据读写、插件装卸、终端、`workspace:write`）→ 断言被拒；远端操作仍受该 Agent / 会话 / 工作区既有权限约束 |

模块检查沿用现有 CI；真实登录、Office、音视频与桌面行为按改动范围在本地专项验收。
**浏览器测试不能替代桌面与移动端实机验收。**

## 机构版边界

- 公版不含任何学校专属逻辑：不含机构域名、SSO 方式、服务发现与校园网穿透实现。
- 机构版按 `docs/EDITIONS.md` 在 `edition/plugins/` 提供中继与部署适配；
  客户端与协议保持通用。
- 机构版升锁依赖公版**发版**：装配在机构模式校验公版提交与源码回执，
  因此机构集成在公版合入并发布后进行，不在本提案内。
