# 开放远程接入协议与 Web 客户端提案

**简体中文** | [English](README_EN.md)

状态：本提案是**待评审草案，尚未实现**。文中的协议名、帧、字段、配置项、范围词汇与命令都是**设计意图**，
不代表已发布的功能或可直接使用的配置；不应按未发布的提案修改生产配置。
「已核实」标注的条目来自本机实装包的 README 与类型声明，可用文中给出的路径逐条复核；
「推断」「待验证」标注的条目尚未做源码级核对。

归属：公版（EduWork）。学校专属服务与部署细节另案，边界见[机构版边界](#机构版边界)。
关联：issue [#116](https://github.com/ECNU/EduWork/issues/116)、路线图 [#95](https://github.com/ECNU/EduWork/issues/95)。

## 目标

让用户从另一台设备通过浏览器查看并继续本机正在运行的 EduWork 会话、任务与工作区成果。
公共客户端与协议不绑定任何学校或服务端实现；机构或开发者可按协议自行实现接入服务。

三个必须在设计里被回答的问题（来自 #116）：

1. 复用 DSH 连接层的哪些能力，避免维护重复的内核实现；
2. 本机宿主、Web 客户端与中继/接入服务各承担什么职责；
3. 设备配对、身份认证、撤销访问、操作授权、状态同步与断线恢复如何设计。

## 一句话结论

**DSH 0.2.0-rc.2 已经把「浏览器 ↔ Host」这一整条线做完了。**
本提案不新造协议栈，而是给已有的 **Connection 载体层增加一个可远程承载的实现**，
再补上它今天明确不做的三件事：**设备身份、可单独撤销的授权、非 loopback 的传输安全。**

支撑这一结论的三条已核实事实见[与既有实现的关系](#与既有实现的关系)。

### 为什么不用 SDK 协议作底座（已核实）

`dsh-sdk-protocol` 是本仓库唯一已存在的对外协议，但它**不能**承担远程接入：

- 传输是 **stdio**，不是网络；
- 已知限制原文：「**无协议版本协商** —— 握手只携带 `serverInfo.version`（`0.0.1`，客户端不校验）」；
- 已知限制原文：「**无取消与会话关闭方法** —— 客户端放弃轮次的方式是关闭运行时进程」；
- 「**没有逐提示词结果** —— `MessageId` 只标识 inbox 准入」；
- 它没有工作区、成果、审批与设置面。

**但它的分层值得照抄**：一个纯协议库（无插件、无配置、无注册）+ 一层薄展示适配器插件，
两侧共用同一份具名类型；协议结构被 Python SDK **复现而非导入**，因此改方法/载荷时必须在同一次变更里同步对侧。

### Peer 契约刻意不记录身份与权限（已核实，本提案的立论基础）

`dsh-typert-protocol/lib/types/types.d.ts`：

```
L294  /** Opaque identity of one Peer: a party admitted to this Host by the connection
L295   *  layer. "Peer" is a connection-layer word; … */
L300  /** One Peer's session on this Host. Connection owns it: `ctx` is the Cordis …
L302   *  Peer. Who the Peer is and what it may do are not recorded here. */
L326  /** Peer the call speaks for; an in-process carrier speaks for the operator. */
L327  readonly peer: PeerScope
```

两条原文合起来说明：**「Peer」是连接层的词**；Peer 契约**只**表达「本次调用代表谁」，
**不**记录该 Peer 是什么，也**不**记录它可以做什么。

因此「远程设备 Peer」在外围实现是**契约允许**的：`OperatorPeer` 是唯一现存实现，
但契约本身没有假设只有一个 Peer，也没有假设 Peer 必须是本机操作者。
权限（what it may do）按同一段注释的划分，本来就不属于 Peer，而属于**传输层围栏 + 装配清单**。

> **注意**：`@deepseek-ai/dsh-authorization` **不是** Peer/RBAC 授权。它是「获取必须由人交出来的凭据」的
> flow 注册表（OAuth 式登录、一次性码）。它的已知限制原文写着「**没有吊销** —— 登出即
> `ctx.credentials.deleteRecord(key)`，它只遗忘本地记录而不通知签发方」。**不要把它当作设备授权的底座。**
> 值得借用的是它的范式：「seam 拥有对话，从不拥有协议」与「**交互随请求传入，而非注册表**」——
> 发起授权的一方才是能与人对话的一方，因此提问恰好抵达发问的那个界面。设备配对正需要这个形状。

### 桌面壳已经在用「壳自有的载体」（已核实其适配层）

`dsh-electron/src/native-web-host.mjs` 显示：EduWork 桌面壳**把官方 Host 起成真实的 loopback HTTP 服务**
（并断言必须是 `http://127.0.0.1:<port>`、无凭据、端口非空，否则停止 Host 并抛
`Host reported an invalid loopback address`），然后：

1. `authenticateWebHost(ready.url)` 取得 Cookie；
2. 用特权自定义协议 `dsh-app://app/...` 提供文档；
3. `forwardWebRequest(request, origin, cookie)` 把其余请求转发到 loopback origin，**注入 Cookie 与 `sec-fetch-site: same-origin`**；
4. `socketHeaders()` 只放行来自 owner `webContents` 且 `origin === 'dsh-app://app'` 的 WebSocket 升级，并改写为 origin + cookie；
5. `boot()` 返回 `{ injections, streamBaseUrl: this.#ready.origin }`。

> **证据边界**：`native-web-host.mjs` 在 `main` 上可读；但它 import 的 `./web-document.mjs` 与
> `./eduwork-native-host-process.mjs` **不在** `dsh-electron/src` 目录列表里，且
> `dsh-electron/scripts/native-desktop-source.mjs` 只改写 `main.ts` / `preload-app.ts` /
> `microphone-permissions.ts` / `fatal-recovery.ts` 四个文件、**不生成**这两个模块。
> 结合 `dsh-electron/README.md`「Electron 主进程、窗口、`dsh-app://` 和**流式 Host 传输**从该提交派生」，
> 推断 `dsh-app://` 与流式 Host 传输是 **DSH 官方桌面能力**而非 EduWork 自造。
> 此项标记为**推断**，实现前需在能跑构建的环境里核一次。

**意义**：远程载体的实现有**本仓库内可对照的先例**——同一套思路（壳/载体持有凭据并代为转发）
换成「第二台设备的浏览器」这一承载对象。

## 三层职责

```
┌──────────────────── 本机宿主（Host）────────────────────┐
│  已有：session / agent / tools / workspace / credentials │
│  已有：载体中立 RPC + Fetch 路由注册表                    │
│        Gateway /api/remote.mux + stream-protocol 帧       │
│        API Remotes 装配清单（决定对客户端开放哪些能力）    │
│  新增：remote-access 宿主插件                             │
│    · 远程载体（第三个 carrier），自带准入                  │
│    · 设备登记表（公钥 + 授权范围 + 状态）                  │
│    · 配对服务（发起配对的设备在等回答）                    │
│    · 范围围栏（默认拒绝，endpoint 白名单）                 │
│    · 审计记录（谁、何时、做了什么，本机可见）               │
└──────────────────────────────────────────────────────────┘
                          │ eduwork-remote/v1
                          ▼
┌────────── 中继 / 接入服务（可选、可替换、可自托管）──────────┐
│  只管：可达性（NAT 穿透 / 反向隧道 / 端口转发）、             │
│        TLS 终止、配对会合（rendezvous）、在线状态             │
│  不持有：会话内容、凭据、明文载荷                             │
│  机构或开发者按协议实现；公版仓提供最小自托管参考实现          │
└──────────────────────────────────────────────────────────┘
                          │
                          ▼
┌──────────── Web 客户端（通用，不绑定学校）────────────┐
│  复用现有 SPA 与 ctx.remote 契约                        │
│  新增：配对 UX、设备凭据（WebCrypto 不可导出私钥）、      │
│        移动浏览器适配、断线恢复 UI                       │
└────────────────────────────────────────────────────────┘
```

职责划分的一条硬规则：**中继是可选项。** 不需要中继时（同一 LAN、已有 VPN、端口转发）
功能必须完整可用。这样中继故障或下线**不影响本机与客户端的基本可用性**，
这是本提案对「维护成本」这一问的核心回答。

## 协议草案 `eduwork-remote/v1`

### 握手

```
客户端 → Host
{ "type": "hello",
  "protocol": "eduwork-remote/v1",
  "deviceId": "<已配对设备的稳定标识>",
  "client": { "name": "示例设备", "platform": "browser|android|ios|desktop",
              "appVersion": "0.1.0" },
  "capabilities": ["stream.v1", "events.v1", "journal.v1"] }

Host → 客户端（成功）
{ "type": "welcome",
  "protocol": "eduwork-remote/v1",
  "host": { "home": "<用于缩写路径>", "appVersion": "0.4.2",
            "dshVersion": "0.2.0-rc.2" },
  "session": { "id": "<本次远程会话标识>", "expiresAt": "<绝对时间>" },
  "scopes": ["session:list", "session:read", "session:prompt"],
  "resume": { "supported": true, "cursorTtlMs": 600000 } }

Host → 客户端（失败）
{ "type": "reject",
  "code": "unauthorized" | "revoked" | "version-unsupported" | "scope-empty",
  "message": "…" }
```

### 版本与能力规则

- 双方各自声明 `protocol`。**主版本不同即拒绝**（`version-unsupported`），**不做自动降级**。
  这与仓库既有取向一致——网关认证提案原文：「未知版本、冲突标志或缺少关键能力必须报错，不在授权失败后自动降级。」
- `capabilities` 取交集；客户端**不得**在 Host 未声明某能力时发送对应帧。
- **数据面帧格式复用 `dsh-api-gateway/stream-protocol`**，不另立一套：

  ```
  Client→Host: open{streamId,endpoint,payload} | item{streamId,value?} | end{streamId} | cancel{streamId}
  Host→Client: item{streamId,value?} | error{streamId,error{code,message,details}} | end{streamId}
  ```

  v1 只在其**外面**加一层握手与 scope 声明。**不要在该帧里新增版本字段**——版本属于握手，
  帧保持与浏览器客户端逐字一致，才能共用解析器。

### 幂等与恢复（对应验收项「断线重连不会重复执行操作」）

- **有副作用的一元调用**（v1 中即 `session:prompt` 一类）必须携带客户端生成的 `requestId`。
  Host 在 TTL 内按 `(deviceId, requestId)` 去重：重复到达返回**同一结果**，不产生第二条用户消息。
- **流**复用 `ctx.remote.$stream()` 家族：`RemoteJournalStream` 提供 follow-before-page、分页、
  重连追赶与缺口修复，并**丢弃完整重复项**、拒绝缺口与倒置区间。
- 上游既定事实（已核实）：「**单向通知不会重放**……需要可靠恢复的状态必须由拥有方提供查询、游标或初始基线。」
  因此**状态同步必须由 Host 侧提供查询面或游标**，不依赖通知补发。这是设计要求，不是可选优化。
- 另两条上游限制决定了不能靠重放：（a）「上行项**不会跨载体代际重放**，需要恢复上行的领域在重开的请求里自带确认游标」；
  （b）`websocketHeartbeatIntervalMs` 同时是 Ping 周期与 Pong 截止时间，网络可能停顿超过该间隔的部署**必须调大**该配置。

### 授权范围词汇 v1（默认拒绝）

| 范围 | 含义 |
| --- | --- |
| `session:list` / `session:read` | 列出与读取会话 |
| `session:prompt` | 向会话投递用户消息（有副作用，需幂等键） |
| `session:cancel` | 取消正在进行的轮次 |
| `workspace:list` / `workspace:read` | 列出与读取已登记工作区文件 |
| `artifact:read` / `artifact:download` | 读取与下载 Studio 成果 |
| `settings:read` | 读取设置（不含凭据） |
| `approval:respond` | 响应审批提示。**独立范围，默认不授予** |

**v1 明确不授予**：任何凭据读写、插件安装/卸载、终端、以及 `workspace:write`。

理由：#116 原文要求「**远程操作应延续本机权限，不能自动扩大授权**」。默认拒绝 + 显式授予，
是唯一能在实现里被验证的满足方式；`approval:respond` 单独列出，是因为让远端设备代替本机点击
「允许」等价于间接提权。

### 设备配对与身份

1. 本机 EduWork 打开「远程连接」面板，生成**一次性、短时效**配对码与请求范围清单；
2. 在另一台设备打开接入地址，输入/扫描配对码；
3. 该设备在**本地**生成非对称密钥对（WebCrypto，私钥不可导出），把**公钥** + 设备名 + 请求范围发给 Host；
4. **Host 侧必须由人在本机确认**，界面显示设备名与将授予的范围；
5. 后续连接使用 **challenge-response 签名**认证，**不使用长期 bearer token**。

### 撤销

删除设备登记记录即完成撤销：Host 立即关闭该设备的活动连接，并作废该设备的 scope 会话。

**为什么设备凭据必须是独立于 Cookie 的第二套**（已核实）：现有连接层「**没有 logout 操作**」——
清除浏览器 Cookie 只结束一个浏览器会话，撤销全部会话需要「删除 owner 凭据记录并重启 `dsh`」。
用 Cookie 做远程认证将**无法**满足验收项「撤销授权后连接失效」。
同时，Cookie **刻意不加 `Secure`**（因为随附服务器走 loopback HTTP），上游原文已警告
「把同一 authority 暴露到明网传输上会让 bearer cookie 在途中泄露」。

### 传输安全边界

- 本机侧继续**只**绑定 `127.0.0.1`；`dsh web --host 0.0.0.0` **保持不支持**，本提案**不放松** loopback 围栏。
- 远程载体是本机进程内的**第三个载体**，对外只经中继或用户自建的隧道；
- TLS 由中继终止，或由用户自建隧道提供；公版不内置公网 TLS 证书管理；
- `trustedHosts` **不用于**远程接入（已核实：它必须是 canonical bare authority，**没有通配语义**，
  且非规范写法会让插件加载失败）。

## 会话与文件访问边界

- 远程客户端**只能**访问 `session:list` 返回的会话与 `workspace:list` 返回的文件；
  不提供任意路径读取，避免变成通用的本机文件读取面。
- 工作区文件读取沿用现有 `dsh-fs` 与 `dsh-fs-sandbox` 的边界，**不新开旁路**。
- 成果下载沿用 Gateway 的附件与精确 Fetch 路由机制（含 range 与流式响应），不另建下载通道。
- 审计记录留在本机，本机界面可见；**不写入会话日志**，避免把设备信息带入模型上下文。

## 客户端边界

- **复用候选**：`dsh-web-frontend/dist`。理由（已核实）：`ctx.remote` 明确被设计为
  「**不依赖 React** 的约定」，上游原文亦称「Web 或**未来的 TUI** 只要提供同一份约定，均可复用其 Client face」。
- 若复用受阻（例如 dist 与桌面壳的自定义协议耦合），退路是构建一个只依赖 `ctx.remote` 约定与
  `stream-protocol` 解析器的精简客户端。**该取舍留待评审确定**，见[尚待明确](#尚待明确)。
- 移动浏览器适配：目标基线为移动端主流浏览器；桌面壳与 `file://` / `dsh-app://` 相关行为**不适用**于远程客户端，
  需独立验收。

## 部署方式

四级形态，**复杂度递增、能力不递减**：

| 级别 | 做法 | 需要新增的服务 | 新增端口 | 典型链路 |
| --- | --- | --- | --- | --- |
| **L0 同 LAN** | 同一局域网直连 | 无 | 一个内网端口 | 局域网 |
| **L1 已有 VPN** ⭐ | 本机与远程设备都加入**用户已有的** VPN | **无** | **无**（复用既有隧道） | 由用户 VPN 决定 |
| **L2 自建反向代理** | 在用户既有的反代上**只增**一条指向本机 `127.0.0.1` 的路由 | 一个绑回环地址的轻量进程 | 无（复用既有 443） | 公网，受跨境/上行带宽限制 |
| **L3 信令与数据分离** | L2 只承载信令；数据面直连打洞或回到 L1 | 同 L2 | 无 | 直连 |

**L1 是推荐首选**：它不需要部署任何新服务、不需要新开端口、不引入新的合规面，
只要求用户已有的 VPN 两端可达。本提案不要求用户为此采购任何东西。

### 中继应当拆成两条路径

这是从真实链路约束反推出来的设计，不是偏好：

| 路径 | 承载 | 对链路的要求 | 可由谁承载 |
| --- | --- | --- | --- |
| **信令 / 会合** | 配对码交换、设备公钥登记、端点发现、在线状态 | 极低（字节级，容忍高延迟） | 任意小配置反代，够用 |
| **数据面** | 会话事件流、提示词、成果字节 | 高（带宽 + 低延迟） | 直连打洞、用户 VPN，或局域网 |

**附带的安全收益**：数据面不经过中继时，中继**在物理上**就看不到内容 —— 这比「承诺不看」可靠。

### 中继实现的硬性约束

- **必须极轻量**：中继可能跑在内存只有几百 MB 的共享小机器上，不得要求重型运行时、
  不得要求在中继主机上构建，不得引入容器编排依赖。
- **必须与既存服务共存**：中继很可能与用户其他服务共用一台反代主机。
  因此接入方式必须是**只增不改**（追加自己的路由/上游），并且**不得要求整份重载反代配置** ——
  整份重载会冲掉只存在于运行时、未写入配置文件的路由。这一点在真实共享主机上是已被验证的坑。
- **部署位置与合规由部署方决定**：部分司法辖区要求面向公众的 Web 服务完成备案，
  而私有 VPN 端点不受此限。因此协议**不假定中继的地理位置**，
  只要求「中继可由机构或开发者自行选择部署位置，并自行承担当地合规要求」。
- **中继不可信**：设备身份在**端到端**层面校验（challenge-response 签名），
  不依赖中继转述的身份。中继被攻陷不得导致越权。

### 「通用客户端不绑定学校服务」的落地方式

客户端只认 `eduwork-remote/v1` 与一个接入地址，**不内置**任何机构域名、登录方式或服务发现；
机构差异全部落在中继与机构版插件里。

## 兼容性边界

- 新增一个独立宿主插件与一条新增的远程载体，**不修改**现有插件的公开导出、配置标识与数据路径。
- **不修改** `BrowserAuth`、`api-request-trust` 的 loopback 围栏语义，**不修改** `dsh web` 的 host 行为。
- **不新增**运行时依赖，**不改**依赖锁，**不新增**需单独发布的 npm 包。
- 发行清单新增一行插件登记，不改变既有插件的顺序与配置；无历史数据迁移（首次引入）。
- 唯一需要评审的公开接口是 `eduwork-remote/v1` 的握手与范围词汇。
- 桌面端与机构版行为不在本提案的实现范围；桌面行为需独立验收。

## 不做什么

- 不新增 RPC 协议或帧格式；不复制 Gateway 的 mux 与退避策略；
- 不修改 `BrowserAuth` 与信任围栏；不把 `--host 0.0.0.0` 变成受支持的部署姿态；
- 不在公版实现学校 SSO 或机构服务发现；
- 不引入第二套桌面壳。

## 开发拆分与验收

阶段划分：**先文档、后骨架、再协议、最后中继**。每个 PR 报告**实际执行的验证与未验证范围**。

1. **本提案（仅文档）**：`docs/proposals/remote-access/README.md` + `README_EN.md`。
   运行 `node scripts/check-source-docs.mjs`。本 PR 不含任何代码。
2. **骨架插件**：`dsh-plugins/remote-access/`，注册「远程连接」设置面板与设备登记表的本地 CRUD，
   配对只在同 LAN 内用合成数据跑通；不改协议。验收：面板可用、登记表重启后保留、`node --test` 单元测试。
3. **协议与握手**：握手、版本协商、能力交集、范围围栏、幂等键与 `RemoteJournalStream` 恢复。
   验收：合成契约测试（版本不匹配报错、能力缺失拒绝、未授权 endpoint 被拒）。
4. **中继参考实现**：最小自托管 server，**不进公版发行清单**；或按评审判定放入独立仓。
5. **Web 客户端**：配对 UX、设备凭据、移动浏览器适配。

**#116 验收关注 → 验证方式**（每条都要能被别人重复）：

| 验收项 | 怎么验 |
| --- | --- |
| 跨设备继续同一任务 | 设备 A 发起轮次 → 设备 B 列出并读取该会话 → 从 B 投递一条消息 → 断言轮次在同一会话上继续、且设备 A 界面实时反映 |
| 断线重连不重复执行 | 在 `session:prompt` 进行中断网 → 重连后重发同 `requestId` → 断言会话中**只有一条**用户消息 |
| 未授权设备不能访问 | 无凭据 / 错误凭据 / 错误 scope 各跑一次 → 断言在任何 RPC 分发**之前**即被拒（401/403），且**没有任何会话或文件字节**过线 |
| 撤销授权后连接失效 | 撤销设备 → 断言活动连接立即关闭、该设备会话作废、重新认证失败 |

模块检查沿用现有 CI；真实登录、Office、音视频与桌面行为按改动范围在本地专项验收。
**浏览器测试不能替代桌面与移动端实机验收。**

## 机构版边界

- 公版不含任何学校专属逻辑：不含机构域名、SSO 方式、服务发现与校园网穿透实现。
- 机构版按 `docs/EDITIONS.md` 在 `edition/plugins/` 提供中继与部署适配；

- 机构版升锁依赖公版**发版**：装配在机构模式校验公版提交与源码回执，
