# Contributing

[简体中文](CONTRIBUTING.md) | **English**

Thank you for improving `dsh-oidc`. Authentication and credential code has a higher review bar than ordinary UI changes.

## Before starting

- Use a public issue for non-sensitive design/bug discussion.
- Use the [private security-reporting entry point](https://github.com/ecnu/EduWork/security/advisories/new) for vulnerabilities or secrets.
- For a protocol or trust-boundary change, open a design issue and add an ADR under `docs/decisions/` before implementation.
- Do not include production endpoints, identifiers, logs, tokens, personal data, logos, or screenshots without explicit publication approval.

## Development

Requirements: Node.js 22+ and npm.

```bash
npm ci
npm run check
```

Use placeholder domains under `example.com`, `example.edu`, or `example.net`. Unit tests must use generated keys and synthetic subjects.

## Pull request requirements

Every PR must:

- explain the user/security impact and affected boundary;
- include tests for success and negative/failure behavior;
- update schemas, OpenAPI, prose, examples, and changelog when a contract changes;
- preserve fixed callback/Key Binding paths unless introducing a versioned migration;
- keep profiles declarative and reject unknown executable-relevant fields;
- use official DSH/community capabilities where appropriate rather than introducing a parallel runtime;
- pass `npm run check` from a clean install;
- declare any new dependency, license, install script, and why it is necessary.

Changes to OIDC, Key Binding, credentials, Profile validation, the native account contract, build/release workflows, or dependency pins require independent technical review, CI, and focused regression evidence, with explicit acceptance by the current maintainer. After a second maintainer joins, these changes should also receive independent human approval.

## Code style

- Native ESM, Node 22 baseline.
- Small explicit modules and fail-closed validation.
- Public error codes are stable machine facts; messages must not contain secrets.
- Network operations need timeouts and bounded response bodies.
- Avoid logging response bodies, headers, tokens, keys, or full profiles.
- Prefer official DSH services and exports; document every compatibility seam.

## Commit and release hygiene

- Keep commits reviewable and signed where project policy supports it.
- Do not commit generated credentials, `.env`, archives, or session logs.
- `lib/` is generated by `npm run build`; review the source and tarball, not only minified output.
- Prefer protected tags and the approved Trusted Publishing workflow. Until that path is configured, the initial maintainer may publish the frozen, verified tarball with the npm CLI and browser 2FA, but must not claim provenance. Record provenance only after npm actually creates an attestation.

By participating, contributors agree to follow [`CODE_OF_CONDUCT.en.md`](CODE_OF_CONDUCT.en.md) and certify that they have the right to submit their contribution under the MIT license.
