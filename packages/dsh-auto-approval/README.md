# 自动审批插件

**简体中文** | [English](README_EN.md)

`@eduwork/dsh-auto-approval` 在专门的权限预设下，先审查命令（bash/pwsh）和文件工具（write/edit/apply_patch）越出沙箱的申请：固定规则和 SystemOne 兼容的决策模型都认为用户会同意的，直接放行这一次；其余申请原样交给确认卡，由用户决定。插件不会替用户拒绝申请。

插件使用 DSH 原生的审批、工具和配置机制，无 runtime 补丁。服务地址、模型及认证均由用户或发行版提供，包内没有默认机构或公共推理地址。

## 审查方式

审查只发生在同时满足以下条件时：会话选择的是插件配置的预设（默认 `auto-approval`）；申请来自 `bash`、`pwsh` 或文件工具 `write`、`edit`、`apply_patch`；调用带有 `sandbox_permissions`，需要越出当前沙箱；其他工具策略（如 hooks）没有要求先问用户。MCP 等其他工具的审批，其他策略要求确认的调用，以及其他预设下的会话，都不受影响。

插件把这次申请整理成一份状态交给决策模型，字段依次为：系统、工作区（沙箱允许写入的范围，即会话开始时的目录）、当前目录（命令实际运行的目录）、本次会话创建的文件、用户回复的助手消息、用户最近的消息、申请理由、之前执行的命令、风险标记、待执行的命令；bash 命令只是运行一个本地脚本文件时（如 `bash scripts/deploy.sh prod`、`python3 tools/sync.py`、`./run.sh --all`），再附上脚本内容。

文件工具的申请按效果相同的写法放进“待执行的命令”：`write` 写成 `cat > 路径 <<'EOF'` 的 heredoc，`edit` 写成补丁，`apply_patch` 保持原样；写入的内容每段最多保留 4000 字。状态最后再加一项“目标文件”，列出每个要改的文件经过链接后的真实路径，以及它是新建、整个替换、修改、删除还是移动，是不是本次会话创建的。

用户在智能体的提问卡上作答，也算用户的消息（如“选择“删除””），它回复的助手消息就是这张提问卡；在提问卡等待期间作答和超时后作答都算。

固定规则标出必须由用户明确要求的操作：推送和发布、远程连接、上传、运行部署或发布脚本、钥匙串和凭据、sudo 和提权、安装、改软件配置（含 `~/Library/LaunchAgents` 里的登录启动项）、系统设置。规则同样检查命令要运行的脚本内容。文件工具按每个文件的真实路径套用同样的规则，相当于对这个路径执行 `cat >`、`rm` 或 `mv`：写到 shell 启动文件或 `~/.config` 下算改软件配置，删 `~/.ssh` 下的文件算钥匙串和凭据。

- 命中规则：模型只回答一个问题，即用户是否明确要求过这件事；概率不低于 0.7 才放行。
- 未命中规则：并行问两个问题，即用户会不会同意，以及做错了后果有多严重；两者平均（同意概率与 1 − 严重程度取均值）不低于 0.5 才放行。
- 文件工具要改本次会话之前就有的文件时，分数取上面的平均值和同意概率中较小的一个：用户要求了这次改动，而且后果容易撤回，才放行。改动再小，模型认为用户没要求的也交给用户。

放行只对这一次申请有效，不记住。用户在确认卡上拒绝过越界申请后，到用户发下一条消息之前，这个会话的越界申请不再审查，直接交给用户。

## 安装和配置

在 DSH 插件管理中安装 `@eduwork/dsh-auto-approval`；原生 bundle 使用固定 ID `auto-approval`，默认 `enabled: false`。

插件本身不能新增权限预设，需要在 DSH 权限插件（ID `permission`）的配置里加一个沙箱为 `workspace-write`、审批为 `ask` 的预设。配置会整体替换原有预设表，所以要把原有预设一起写上：

```json
{
  "presets": {
    "read-only": { "sandbox": "read-only", "approval": "ask" },
    "workspace-write": { "sandbox": "workspace-write", "approval": "ask" },
    "auto-approval": {
      "sandbox": "workspace-write",
      "approval": "ask",
      "name": "自动审批",
      "description": "工作区外的操作先由决策模型审查，拿不准时再问你"
    },
    "danger-full-access": { "sandbox": "danger-full-access", "approval": "never" }
  }
}
```

DSH 只给内置的四个预设画了图标，插件的界面部分给 ID 为 `auto-approval` 的预设补上一个：输入框旁的权限菜单里，放在其他预设图标的位置；选中这个预设时，权限按钮上也显示。界面部分读不到插件配置，`preset` 改成别的预设就不加图标；有别的预设和它同名时分不清是哪一个，也不加。设置页的“默认权限”和 `/permission` 列表里所有预设都没有图标，那里也不加。以后 DSH 改了菜单结构、找不到对应位置时不加图标，菜单照常使用；DSH 自己给这个预设画了图标时，用 DSH 的。

插件配置示例（在凭据服务中保存真实 Key，不把 Key 填进此配置）：

```json
{
  "enabled": true,
  "preset": "auto-approval",
  "baseURL": "https://decision.example.org/v1",
  "model": "your-decision-model",
  "authMode": "api-key",
  "credentialRef": "SYSTEMONE_API_KEY",
  "timeoutMs": 10000
}
```

`baseURL` 包含 API 前缀，请求沿用 [`@eduwork/dsh-decision`](../dsh-decision/README.md) 的客户端。机构登录选择 `authMode: "oidc"` 并填写 `oidcProfileId`，需要兼容的 `@eduwork/dsh-oidc`；明确免鉴权的服务才选择 `authMode: "none"`。

## 失败与超时

- 一次审查的总时限为 `timeoutMs`（默认 10 秒，决策服务繁忙时一次审查要 3～6 秒），超时交给用户确认。
- 网络错误、429 和 5xx 在时限内重试一次；问题本身不产生副作用。
- 同一会话连续失败 3 次后暂停审查 5 分钟，期间申请直接交给用户。
- 回答缺字段、服务拒选（`choice: null`）按失败处理。
- 未登录机构账号（`baseURL` 和机构账号的服务地址不一致时也算）或没有 Key 时，不发请求，直接交给用户，记录里写明原因；这不算失败，不会暂停审查，登录或存好 Key 后，下一个申请就会审查。
- 以上情况都不回退到其他模型或认证方式。
- 用户在审查期间撤回申请，不计入失败。

## 查看审查结果

预设下审查的每个申请，都会随这次调用的结果在会话里留一条记录，写明自动审批放行了这次越界申请，还是交给了用户确认。“轨迹”里它是一行“上下文”；点开后在“来源”里能看到结果和分数，例如“已自动放行（分数 0.952）”“交给用户确认（命中规则，分数 0.600）”，没有审查出结果的写明原因：未登录机构账号、没有决策服务 Key、审查超时、审查失败、连续失败暂停审查、命令过长未审查、用户拒绝过未审查、审查期间情况有变。

这条记录也会在下一步发给对话模型。它和 DSH 自己的运行时上下文一样用 `<system-reminder>` 包着，并写明不是用户发的消息，所以智能体既不会把自动放行说成用户批准的，也不会把记录当成用户说的话；分数不发给模型，免得智能体照着分数改申请理由。DSH 的对话界面不显示这类注入的上下文，所以只在轨迹里看得到。

每次审查还在日志 `auto-approval` 中记录结果、分数和耗时，失败时记录警告和原因。

## 发送给决策服务的内容

状态里包含用户最近 3 条消息（超过 300 字的保留开头 100 字和结尾 200 字）、用户回复的那条助手消息（最后 1000 字）、之前 6 条命令（每条前 300 字）、本次会话用 `write` 新建的最近 8 个文件路径、命令要运行的脚本（最多 16000 字），以及文件工具要写入的内容（每段最多 4000 字）和要改的文件路径。启用前请确认决策服务可以接收这些内容。

## 评测与限制

规则和问法在 6 组共 419 条真实越界申请上评测（每组都先标注“应当放行”或“应当询问”再运行）：自动放行 284 条（68%），134 条应当询问的申请没有一条被放行。评测用的是一个 SystemOne 兼容的决策模型；换用其他模型需要重新评估。

文件工具的审查用其他编程智能体会话里真实的工作区外写文件操作评测，按插件的方式整理后交给同一个决策模型：应当放行的 141 条放行了 109 条（77%）；应当询问的 35 条没有一条被放行，其中 3 条是真实申请，32 条是把对已有文件的改动配上另一个任务的上下文构造出来的。“改已有文件要用户要求过”这一条是看过第一批结果后加的；加上以后另抽一批留出样本只跑了一次：应当放行的 33 条放行了 25 条，应当询问的 15 条全部交给用户。

超过 300 字的用户消息保留开头和结尾，因为回复引用内容时，用户自己的话通常在最后。在上面两类评测里含长消息的 113 条上（应当放行 91 条、应当询问 22 条）比较过：只留前 300 字放行 75 条，只留最后 300 字放行 75 条，开头 100 字加结尾 200 字放行 78 条；三种截法下应当询问的都没有被放行。

- 子智能体：DSH 把子会话的审批固定为 `never`，越界申请在审批之前就被拒绝；插件也不审查子智能体会话，因为其中的“用户消息”来自委派它的智能体。
- “本次会话创建的文件”只记录 `write` 成功新建的文件，按真实路径比对；补丁的 Add File 可能覆盖已有文件，和命令新建的文件一样不计入；Host 重启后从空开始。所以这些文件，文件工具再去改时按已有文件对待。
- 确认卡保持原样，不显示审查结果。
- 超过 16000 字的命令不审查，直接交给用户；评测数据里最长的命令约 13000 字。文件工具按截断内容后的长度计算。
- 规则按命令文本匹配。脚本内容只在整条 bash 命令就是运行一个写明路径的脚本时才附上，脚本再调用的其他文件不读取；命令序列、`cd`、变量（包括命令前的 `NAME=value`）、通配符、管道、重定向、路径里的 `..`、`node -e` 这类内联代码、不带路径按名字运行（由 shell 在 PATH 里找）以及 PowerShell 命令，都看不准实际运行的是哪个文件，不附脚本，命令本身照常审查。

## 开发与装配

源码在 `src/`，构建复制 ESM 模块，并把不引用其他模块的界面部分 `src/client.cjs` 包装成 DSH 客户端模块。Node >=24.22.1，已在 DSH 0.2.2-rc.1 上验证。将 `EDUWORK_AUTO_APPROVAL_RUNTIME` 指向锁定 Runtime（含 package.json/node_modules 的目录），运行 `npm ci`、`npm run check`；测试使用合成材料与本地 HTTP，并在真实 Runtime 上跑通从模型发起申请到审批完成的流程。

仓库统一入口为 `node scripts/packages/manage.mjs check dsh-auto-approval` 和 `pack dsh-auto-approval`，详见[包维护指南](../../docs/PACKAGES.md)。正式产品需先发布并核验 npm 原包，再更新精确锁。
