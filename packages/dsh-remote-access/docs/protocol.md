# 远程接入协议 v1（`eduwork-remote/1`）

这份文档描述**远端设备**与**本机宿主**之间的契约。它不依赖任何特定学校、机构域名或公共服务：
中继是可选组件，设备配对完全在本机完成，协议本身只假设「有一台跑着 DSH 的机器」。

## 1. 角色

```
远端设备 ──► 门禁中继 ──► 宿主（DSH，只监听回环）
（浏览器）   （本机）      （本机）
```

| 角色 | 职责 | 不做什么 |
| --- | --- | --- |
| **远端设备** | 出示设备凭据；携带 `requestId` 发起有副作用的调用 | 不接触宿主令牌；不管理宿主 |
| **门禁中继** | 准入门禁、配对、逐设备撤销、切断活动连接 | 不重发请求；不代为去重；不改写载荷 |
| **宿主** | 持有会话与工作区；按 `requestId` 保证至多一次准入 | 不对网络暴露 |

**中继是可选组件。** 同 LAN、自建 VPN、端口转发都必须能在没有中继的情况下工作；
协议不假设任何特定外部服务存在。

## 2. 凭据

四类凭据**彼此独立，不得混成同一个令牌**：

| 凭据 | 作用 | 生命周期 | 存放 |
| --- | --- | --- | --- |
| 配对邀请 | 「允许一台设备接入一次」 | 一次性，短时 | 只存摘要 |
| 设备凭据 | 「我是哪台设备」 | 长期 | 只存摘要 |
| 中继接入 Key（可选） | 「允许使用这台中继」 | 部署级 | 由自托管中继自行决定 |
| 宿主会话 | 「宿主认这个浏览器」 | 由宿主决定 | 宿主自己签发 |

关键点：**中继接入 Key 只表示「允许使用中继」，不能代替设备配对。**
即使中继要求接入 Key，每台设备仍然必须完成一次性配对并经本机确认。

## 3. 控制面：`/__remote/*`

控制面由中继自己应答，**永不转发给宿主**。

### `GET /__remote/pair?token=<邀请码>[&name=<设备名>]`

兑换一条一次性配对邀请。

- **成功** → `302`，`Set-Cookie: eduwork_device=<设备id>.<密钥>; HttpOnly; SameSite=Lax`，
  跳转到 `/__remote/waiting`。
- **失败** → `403`。

失败有四种成因：邀请码不存在、已被使用、已过期、写错了。
**四者必须不可区分** —— 实现上「先消耗、再校验」：
无论哪种情况，邀请都已被消费，因此重放、迟到与错字留下的状态完全相同。
响应内容不得泄露是哪一种。

### `GET /__remote/waiting?next=<确认后跳转的地址>`

配对成功后手机停留的页面。它轮询 `/__remote/status`，确认后自动跳转。

**为什么不直接跳到宿主**：此时设备还是「待确认」，直接跳转会让浏览器
把请求挂在宿主上等本机决定 —— 操作者慢几秒，手机就超时。
等待页把「等」变成可见的进度，慢多久都不影响结果。

### `GET /__remote/status`

携带自己的设备凭据，查询**自己**的状态：`pending` / `trusted` / `revoked`。

只回答调用者自己的状态，不泄露其他设备；无凭据或凭据无效一律 `401`。

### `GET /__remote/devices`

列出已登记设备与活动连接数。

**只允许本机（回环）调用**，非回环一律 `403`。
设备名与编号是操作者的视图；否则任何够得着中继端口的调用方，
包括未配对的，都能把已配对设备枚举出来。

## 4. 数据面

除 `/__remote/*` 外的所有路径。

| 设备状态 | 响应 | 请求是否到达宿主 |
| --- | --- | --- |
| 无凭据 | `401` | **否** |
| 凭据无效 | `401` | **否** |
| 待确认 | 挂起，等本机决定 | 决定为「是」之后才到达 |
| 本机拒绝 | `403` | **否** |
| 已撤销 | `401` | **否** |
| 已信任 | 转发 | 是，`Host` 改写为回环 authority |

**门禁在宿主之前。** 「未授权设备不能访问会话或文件」这条验收，
只有在拒绝发生在请求**穿过门禁之前**时才成立 —— 若 `401` 由宿主发出，
说明请求已经到达宿主，这条验收就是假的。

被转发的请求，`Host` 必须改写为中继所连的回环 authority：
设备自己的地址不是宿主信任的 authority，原样转发会被宿主的信任围栏拒绝。

### 转发的两条硬约束

**`Host` 与 `Origin` 必须一起改写为中继所连的回环 authority。**

只改 `Host` 不够，而且**用 `fetch` 写的测试看不见这一关**。宿主的信任围栏要求「附带的
`Origin` 与它看到的 `Host` 同源」；`Origin` 原样转发时两者必然对不上，结果是浏览器发出的
**每一个 `/api` 调用都收到 `403`**。失败的样子很难归因：页面照常加载，里面什么都不工作，
两侧都没有像样的报错。而 Node 的 `fetch` **根本不发 `Origin`**，围栏在它缺席时直接放行 ——
所以任何只靠 `fetch` 驱动的验证，包括自己写的中继测试，都结构性地看不到这一关。
**只有真实浏览器能证明它。**

**`sec-fetch-site` 不得被规范化。**

它必须保留浏览器写下的原值。这一关拦的是「手机浏览器里某个页面被诱导去驱动宿主」；
中继把它抹平，等于替那个页面签了名。

### 升级（WebSocket）与普通请求走同一道门禁

宿主只在握手返回 **101** 时才让 Node 发出客户端的 `upgrade` 事件。所以一个被拒绝的升级，
在设备侧表现为**彻底的静默**：既没有响应，也没有错误，客户端会一直等一个不会来的握手。

中继必须把上游的拒绝**转写回设备的 socket 再关闭**；只监听 `upgrade` 事件而不管失败，
就等于让被拒绝的设备挂死在那里。

**中继自己的拒绝同样要给状态。** 同一台设备、同一次裁决，普通请求会拿到 `401` 或 `403`，
升级却收到一个没有任何字节的断链 —— 两者不一致，而且在抓包里，一个光秃秃的 reset 和
「网络掉了」无法区分。既然裁决是同一个，答法也该是同一个。

写状态时用 `socket.end()` 而不是 `socket.destroy()`：`destroy` 会丢掉尚未刷出的缓冲区，
刚写下的状态行会被一起扔掉，于是又回到了「客户端什么都看不到」——绕了一圈回到要避免的那件事。

`/api/remote.mux` 是宿主实时通道的路径，它和普通请求一样按设备状态放行或拒绝。
**只给 HTTP 请求设门禁、把升级放过去，是一个静默的授权绕过** —— 撤销一台设备时，
它手里已有的流必须被切断（§5），而没建立起来的流必须建立不起来。

**这条流不是锦上添花，它在「查看工作区成果」的关键路径上。** 宿主没有「列工作区目录」
的接口：工作区的成果经由 `workspace/changes` 一类**事件**送到客户端。因此一台守不住这条
长连接的设备，**看不到工作区里有什么**——不是慢，是没有。中继里那条 WebSocket 通道断了，
表现就是「会话能开、消息能发、工作区永远空的」。

**关闭帧必须连码和原因一起透传。** 退出码与原因（例如 `1008` 加一句拒绝的理由）是客户端
区分「协议错误」与「网络断了」的**唯一**依据。只透传消息、吞掉关闭握手的中间层，会让设备
无法判断刚才发生了什么，而它已经收到的内容又看起来一切正常。

### 数据面的线格式属于宿主，不属于本协议

中继是透明管道：它**不理解也不改写**载荷。远端设备在数据面上说的是**宿主自己的 RPC**，
本协议不重新定义它。但「按这份文档实现」不该意味着「随便转发就行」，所以这里记下 v1
实测到的形状，以及它归谁：

- 请求封套 `{ type: "client-request", rpcId, method, payload: { args: { <形参名>: … } } }`
- 响应封套 `{ type: "server-response", rpcId, result: { ok: true, value } | { ok: false, error } }`
- **形参名由每个方法的描述符决定，各方法并不一致**（`session/create` 用 `request`，
  `session/list` 用 `_request`）；名称不符时宿主会明确回报缺的是哪一个
- 实时通道是 `GET /api/remote.mux` 上的 WebSocket 升级

这些由 `@deepseek-ai/dsh-api-*` 拥有，会随宿主版本演进。正因为如此，**中继的正确行为是
不解析它们**：除了上面那两处必要改写，其余原样透传。中继一旦开始理解载荷，就同时继承了
「和宿主版本保持一致」这个它无法承担的维护义务。

## 5. 撤销

撤销一台设备是**三个动作同时生效**，缺一不可：

1. **删除**它的设备凭据（不是禁用 —— 让「已撤销」与「无法认证」成为同一个状态）
2. **封住**它的设备 id，使撤销瞬间正在握手的连接失败而非溜过
3. **切断**它当前持有的全部连接，包括 WebSocket 与 SSE 流

第 3 条不能省。上游语义明确：*已有的请求在监听器拒绝后续请求时仍会继续*。
一条已经建立的流比一次请求更糟 —— 它会**持续推送事件**，
直到有人把它关掉。只拒绝下一个请求，等于让被撤销的设备继续看着你的会话。

### 设备记录的字段

设备记录只有两个时间戳：`pairedAt`（首次登记）与 `lastSeenAt`（最近一次见到）。

**没有独立的撤销时间戳。** `revokeDevice` 会把 `lastSeenAt` 写成撤销时刻，
此后因为已撤销的设备不再接受 upsert，它就冻结在那里。用来排序事件够用，
但**同一个字段承担了两个含义**，读记录的人需要知道这一点。
加一个 `revokedAt` 是纯增量改动，等有人真的需要区分「最后活跃」与「被撤销」时再做。

### 读不出来的记录会让整张表拒绝加载

`normalizeRegistry` 遇到无法解析的记录会**抛异常**，而不是跳过它。

这是刻意的。跳过一条设备记录本身是安全的 —— 未知设备同样不被信任；
但同一条代码路径也在读**承载撤销的记录**，静默丢掉其中一条，
正是这个包存在的意义所要防的事。所以宁可让操作者看到错误，
也不要给他一张看起来正常、实则少了一条撤销的表。

### upsert 不做状态转换

`DeviceRegistry.upsert` 只回答「这台设备又出现了」，**不接受调用者指定状态**：
新设备一律 `pending`，已有设备保留当前状态，调用者传来的 `status` 被忽略。

两种显而易见的替代都是错的。要求调用者提供，则把它读成「记一笔」的人会收到异常；
采纳调用者的值，则一个习惯性的 `status: 'pending'` 会在设备每次重连时
悄悄撤销操作者的决定，而同样位置上的 `'trusted'` 会**在无人确认的情况下授予访问**。

状态转换有自己的方法：`confirm` 进入 trusted，`revoke` 与 `remove` 离开它。
已撤销的设备 id 不再接受 upsert —— 那等于让调用者改写一个已撤回凭据背后的身份。

## 6. 幂等

**有副作用的调用必须携带客户端生成的 `requestId`。**

宿主把它定为**必填**字段而不是可选项：`session/prompt` 的形状里 `requestId` 与 `sessionId`、
`mode`、`content` 并列，缺了它调用不被接受。设备因此没有「这次不传」的余地。

宿主按 `requestId` 保证**至多一次准入**，且查重覆盖两处：

- 已入队但尚未执行的
- 已落进会话历史的

第一处覆盖的正是最危险的窗口：**请求已经到达宿主，回执在断线中丢失**。
此时设备重发同一个 `requestId`，宿主返回已接受而**不执行第二次**。

因此中继的责任是「三不」：

| 不做什么 | 为什么 |
| --- | --- |
| **不重发** | 重发会把一次丢失的回执变成第二次执行 |
| **不改写** | `requestId` 是重试与原始发送之间唯一的联系，改写等于静默关掉去重 |
| **不代为去重** | 中继若自己吞掉第二次，就把一次**真实的二次发送**藏了起来；只有宿主有资格判断它是不是重复 |

## 7. 版本

当前版本标识 `eduwork-remote/1`。

协商规则沿用仓库既有取向：**未知版本、冲突标志或缺少关键能力必须报错，
不在授权失败后自动降级。**

## 8. 明确不在 v1 范围内

- 远端**不得**访问宿主管理面：配对管理、凭据读写、插件装卸、终端、`workspace:write`。
  这是协议**要求**的行为，但 **v1 没有实现它**。`./gate` 的决策表没有调用方，
  `./listener` 只按路径放行、不看操作；而且要紧的不止是没接线 ——
  中继为了把手机送进宿主自己的门，必须把宿主的启动凭据交给它，
  手机因此持有**完整的宿主浏览器会话**，前面再加一道 HTTP 中继也剥夺不掉宿主已经给出的权限。
  真正的硬闸只能由**宿主自己的授权层**执行。**在它实现之前，不要依赖这一条。**
- 不定义只读／可操作的角色体系 —— 首阶段所有已配对设备都是「本人的操作端」。
- 业务内容的端到端加密不在 v1；v1 的前提是设备与宿主之间的信道由部署方保证
  （同 LAN、自建 VPN 或自建中继的 TLS）。
